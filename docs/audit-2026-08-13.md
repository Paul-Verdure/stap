# Stap — readiness audit

**Date:** 2026-08-13 · **Commit:** `9d6a78f` (main) · **Method:** static checks,
production build, and a full browser walkthrough of the real app (dev server on
:3001, production server on :3002) as a freshly created throwaway user, in both
themes and both locales.

The question this audit answers is threefold: **does it work**, **is it ready
for people other than its author**, and **is it presentable to a recruiter**.

> **Status — 2026-08-14.** All four stages of the plan are done; each finding
> below carries its own resolution note. Two things are deliberately still
> open, and neither is a defect: there is no end-to-end suite (it needs a
> disposable database and a way past the magic link — a test-infrastructure
> decision), and the v2 stubs are still stubs, honestly labelled. One item,
> the Vercel region, is set in the repository but can only be confirmed on
> the next deploy.
>
> Counting changed along the way: what the audit recorded as three
> invisible-selection call sites turned out to be five, and the finding that
> looked like a one-line cron change (F7) turned out to need a data migration
> to avoid silently disabling every reminder.

Short version: the engineering is genuinely strong and the app works
end-to-end. What holds it back is a handful of unfinished *edges* — placeholder
copy on the first screen, `TODO:` markers on the public legal pages, and three
state-visibility defects that automated accessibility testing cannot catch.
None of them are deep; all of them are visible.

### Security posture — no issues found

- **RLS is enabled with policies on all 14 business tables.** Only
  `_prisma_migrations` has it off, which holds no user data.
- **Every server action authenticates** via `supabase.auth.getUser()` and scopes
  its writes by `user.id`.
- **No IDOR on the journal detail route.** `/journal/[id]` queries
  `where: { id, userId: user.id }`, with a comment correctly noting that Prisma
  bypasses RLS so the clause *is* the access control.
- **The cron endpoint fails closed** — missing `CRON_SECRET` returns 401 rather
  than running unauthenticated.
- **The magic-link confirm route rejects open redirects**
  (`/^\/(?!\/)/` blocks protocol-relative `//host`).

This is a better security posture than most portfolio projects ever reach.

## 2. Findings

Severity is judged against the three goals, not against code style.

### P0 — Blocks giving the app to anyone else

#### F1. The public legal pages ship visible `TODO:` markers

`lib/legal-config.ts` still holds `publisher: "TODO: publisher name"` and
`contactEmail: "TODO: contact email"`. These are substituted into the three
legal documents, so a visitor reads:

> "Stap is published by **TODO: publisher name**, an individual…"
> "Contact: **TODO: contact email**"

Six occurrences on the legal notice alone; the tokens appear 12 times per
locale across the documents. The code comment says this is deliberate ("an
unfinished legal notice should be embarrassing, not invisible") — the mechanism
worked, and now it needs paying off. Until it is, **there is no identified data
controller and no route for a privacy or security request**, which is the one
thing you cannot ship to real users in the EU.

#### F2. The first screen anyone sees is developer placeholder copy

`messages/en.json:5` — the welcome page subtitle is:

> "Technical scaffolding in place — soft brutalism design system active."

(French is the same: "Fondations techniques en place — design system « soft
brutalism » actif.") The page component still carries its Phase-A comment:
`// Public entry (welcome). Scaffolding placeholder…`.

This is the landing page for every visitor **and** the page a signed-in user is
bounced to from the profile (see F3). For a recruiter it is the very first
impression, and it reads as an unfinished internal build.

#### F3. "Change password" exists in a passwordless app and dead-ends

`components/profile/account-section.tsx:70` renders a **Change password** row
linking to `/login`. Stap is magic-link only — its own privacy copy says "there
is no password to choose or to lose."

Verified behaviour: tapping it as a signed-in user lands on the **welcome
placeholder page** from F2. A settings row that shouldn't exist, leading to a
page that shouldn't be public-facing.

### P1 — Real defects users will hit

#### F4. The selected state is invisible in dark mode

Three components use `surface-hero` as their *selected* treatment against
`bg-surface`:

- `components/challenge/feel-card.tsx:65` — how did it go? (At ease / Hesitant / Missed)
- `components/ui/lang-card.tsx:38` — onboarding language choice
- `components/games/match-game.tsx:128` — the match game's tile selection

In dark mode the hero background is `#1A1A1A` and the page surface is
`#242220`, and both variants carry the same beige border. Measured contrast
between selected and unselected: **1.10 : 1**. In light mode the same code
measures **16.30 : 1** and looks excellent.

Verified in the browser: after selecting "At ease", the DOM reported
`aria-pressed="true"` while the card was visually identical to its neighbours.
In the match game the tile I had just tapped was indistinguishable from the
other seven — in a game whose entire mechanic is "tap one, then tap its pair".

This fails WCAG 1.4.11 (non-text contrast, 3 : 1 for state indicators) and axe
cannot detect it, because axe does not compare selected against unselected
backgrounds.

**Two further instances found while fixing this**, and worth recording because
of *how* they were missed: the finding above was built from a grep for
`surface-hero`, but `components/ui/chip.tsx` (`Chip`, `TimeSlot`) and
`components/ui/radio-group.tsx` (`RadioRow`) spell the same treatment out
atomically as `border-hero-border bg-hero-bg text-hero-fg`, so they never
matched. Five call sites, not three.

`TimeSlot` was the worst instance in the app: the reminder chips are a
single-select with **no** secondary indicator, so in dark mode there was
nothing at all to show which slot was chosen. `Chip` and `RadioRow` were
partly rescued by their amber check and amber dot. Searching for a token by
name finds the callers that used the token, not the callers that reproduced
it — worth remembering the next time a treatment is retired.

#### F5. The 7-day rhythm is invisible on the hero card in light mode

`components/ui/rhythm.tsx:78`:

```ts
const border = onHero ? "var(--color-hero-border)" : "var(--color-foreground)";
```

`--color-hero-border` exists to outline the hero *card* against the page, and in
light mode it is deliberately `#1A1A1A` — the same as the hero background, so
the card has no visible outline. Using it for the *cells inside* that card
paints ink on ink: **1 : 1**.

Verified on the post-validation confirmation screen: six of the seven day cells
disappeared, leaving one lone square. The component's own comment states the
intent — "rendered onHero so the cells stay visible on ink" — so this is a token
mix-up, not a design decision. The line above it already computes the right
value (`ink`, i.e. `--color-hero-fg`).

This is the emotional payoff screen of the core loop, and it is the default
(light) theme.

#### F6. Three pedagogical tips are undiscoverable

`app/[locale]/(app)/today/prepare/page.tsx:137` — the Tips disclosure is a
native `<details>`, but its `<summary>` carries `className="flex …"`. Setting
`display` on a `<summary>` to anything other than `list-item` **removes the
disclosure triangle**.

Verified: computed `list-style-type: disclosure-closed`, but no marker renders.
The card shows the word "Tips" and nothing else — I read it as an empty section
myself before inspecting the DOM. Behind it sit three genuinely good tips
("Euro stays singular after a number…", "The ij of vijf is the 'ay' diphthong —
FAYF", …). Every other section on the page is expanded by default, so nothing
signals that this one opens.

#### F7. Reminders fire on UTC but are labelled as local time

`lib/push-sender.ts:98` matches the user's chosen slot against
`now.getUTCHours()`. A user who picks "8:00 AM" — and the profile confirms "A
daily nudge, around 8:00 AM" — receives it at 08:00 **UTC**, i.e. **10:00 in
the Netherlands** in summer, 09:00 in winter.

This is documented in `lib/date.ts` as a deliberate simplification, and it is
defensible internally. It is not defensible in the UI, which states a specific
local time it does not honour — for an app whose entire audience is in the
Netherlands.

**Constraint found while planning the fix.** The obvious cheap repair — retime
the three Vercel crons to the UTC hours that land on Dutch local time — does
not work on its own, and fails silently. `sendDueReminders` selects users with
`reminderTime: { startsWith: `${hh}:` }` where `hh` is the *current UTC hour*
(`lib/push-sender.ts:98`), so the stored slot value and the cron hour are the
same number by construction. Moving the crons to 06:00/10:00/16:00 UTC while
the stored slots stay `08:00`/`12:00`/`18:00` matches **zero** users at every
one of the three firings: reminders would stop entirely, with no error.

Matching on Amsterdam local time instead is worse rather than better: with a
cron fixed in UTC, exactly one half of the DST year would miss by a whole hour
and therefore match nobody, instead of merely drifting.

**Resolved 2026-08-14** by option 1 below, then **properly by option 2 on
2026-08-26.** The interim fix made the stored slot the UTC send hour
(`06:00`/`10:00`/`16:00`) and relabelled the UI in words, which was honest but
still delivered at a Dutch hour to everyone.

Option 2 was rejected on a premise that turned out to be wrong: Vercel's Hobby
plan caps each cron *job* at one run per day, but allows **100 jobs per
project**. Twenty-four daily jobs — `0 0 * * *` through `0 23 * * *` — are
therefore legal and give hourly coverage for free; only a single `0 * * * *`
expression is refused. The same loophole the three-cron fix already relied on
simply had more room in it.

So `reminder_time` is now a local slot read against a per-user `timezone`,
Postgres converts with `AT TIME ZONE` (DST included), and the coupling between
slot values and cron hours is gone. Hobby also schedules only to the hour
(+/-59 min) and can skip a firing, so the sender no longer tests hour equality:
it sends when the slot has passed within `CATCH_UP_MINUTES` and records the
local date, which makes a missed firing recoverable instead of silently lost.

So the options were narrower than "shift the schedule":

1. **Retime the crons, remap the stored slots to match, and relabel the UI in
   words** (morning / midday / evening). Matching stays on the UTC hour, so
   nothing breaks; the stored value simply stops being something the user is
   ever shown, which is what makes the label honest in both halves of the year.
   Needs a data migration for existing `reminder_time` values.
2. **Per-user IANA timezone.** Correct for everyone, anywhere. Recorded here as
   needing Vercel Pro for an hourly cron — **wrong**, see above: the Hobby
   limit is one run per job per day, not one job. Adopted 2026-08-26.
3. **Say UTC in the UI.** Ten minutes and strictly true, but "08:00 UTC" means
   very little to a language learner.

#### F7b. The manifest was called complete; iOS had no icon at all

Added 2026-08-26, as a correction to the PWA row above. The manifest did list
192, 512 and maskable icons, which is what "complete" was checked against. All
three were **SVG**, which Safari does not reliably consume for a home-screen
icon, and the app declared no `apple-touch-icon` link and no `icons` metadata
at all — so on iOS there was nothing to show but a screenshot of the page. The
mark also asked for `font-family="Syne"`, which an icon can never load.

The lesson is narrower than "test on a device", and worth keeping: a manifest
was read as a description of what users get. It is a declaration of intent, and
the platforms decide what they honour. Resolved by ADR 0006.

#### F8. The French success banner reads as a failure

`messages/fr.json` — `Today.doneBanner`: EN "Step taken today" → FR **"Pas
franchi aujourd'hui"**, rendered in caps beside a **"FAIT"** badge.

The intent is the noun *pas* ("a step taken"). But without an article, the
default French parse of "pas franchi" is the negation — "not crossed", "not
achieved" — so the completion banner reads as its own opposite, and contradicts
the badge next to it. It also accidentally violates the product's own rule that
a day is never framed as a failure.

Suggested: **"Un pas franchi aujourd'hui"** — the article forces the noun
reading and costs nothing.

#### F9. An amber "New recap" badge promises a screen that does not exist

The profile's "My season" card carries a **New recap** badge — the visual
language of "there is something new for you". Tapping it opens *"Coming in v2 —
This screen isn't built yet."*

The v2 modal copy itself is honest and well written. The badge is the problem:
it actively advertises content before admitting there is none.

### P2 — Smaller inconsistencies

- **F10.** The onboarding recap promises "Your first step: *Greet a colleague in
  Dutch*", but the actual first challenge is drawn by the real selector — mine
  was "Dat is vijf euro." in Shops. The teaser is hardcoded
  (`Onboarding.teaserBody`) and the component comment admits it.
  **Resolved 2026-08-14**: the teaser no longer names a phrase. Selection runs
  server-side once the profile exists, so anything named at that point is a
  guess; it now promises only what is true — a phrase chosen for the contexts
  just picked.
- **F11.** The fill game blanks the *last word* of a phrase with no multi-word
  guard (`lib/game-content.ts:86`). On a single-word catalog entry the round
  collapses to an empty dashed box with no sentence around it — I hit this on
  "één". `content:check` already tracks a multi-word ratio per level (A0 is
  67 %), so the data to filter on exists.
  **Resolved 2026-08-14**: phrases with a sentence around the blank are used
  first. Single-word phrases are still used to top the round count back up
  rather than being filtered out — whole themes are single-word (the numbers,
  the greetings), and a one-round game is a worse outcome than an occasional
  bare frame.
- **F12.** `/[locale]/design-system` is **prerendered into the production
  build** and publicly reachable, with no nav entry and English-only content.
  Either polish it and link it deliberately (it is genuinely impressive), or
  exclude it from production.
  **Resolved 2026-08-14**: kept and documented in the README, so it is a
  deliberate showcase rather than a stray route. Still unlinked from the app
  itself, which is the point — learners have no use for it.
- **F13.** Two code comments still contradict shipped reality:
  `lib/game-content.ts:117` ("currently null for the whole catalog — the game
  renders an honest degraded state") and
  `app/[locale]/(app)/today/prepare/page.tsx:22` ("Audio is wired (disabled
  until clips are synced)"). The audio-shipped cleanup missed these two.
- **F14.** `README.md`'s status paragraph still says catalog audio is
  "deliberately deferred to v2". It shipped; `docs/roadmap-and-deployment.md`
  was updated but the README was not — and the README is what a recruiter reads
  first.
  **F13 and F14 resolved 2026-08-14.**

### P3 — Engineering signals for a portfolio

- **F15. There are no automated tests at all.** No test runner, no test files,
  no `test` script. For a project whose documentation quality is this high, an
  empty test suite is the single loudest negative signal to a reviewer — and it
  is what makes findings F4–F6 possible to ship unnoticed.
  **Resolved 2026-08-14**: Vitest, 73 tests over the pure logic, plus two
  suites aimed squarely at the bug class above — a token-level contrast
  contract and a source guard that fails if the hero treatment is ever used to
  mean "selected" again. The second was added after checking that the first
  did **not** catch a deliberately reintroduced instance: asserting the palette
  is not the same as asserting which token a component reaches for.
- **F16. There is no CI.** No `.github/workflows`. `lint`, `tsc` and
  `content:check --strict` all pass — but nothing enforces that they keep
  passing, and a reviewer cannot see a green check.
  **Resolved 2026-08-14**: `.github/workflows/ci.yml` runs typecheck, lint,
  the catalog check and the tests on push and pull request, with no secrets —
  verified by running the whole sequence locally with `.env` moved aside.
- **F17. The Vercel region is unpinned.** `vercel.json` declares crons but no
  `regions`, so functions run in Vercel's default US East while the database is
  in Frankfurt — a transatlantic round trip on every query, and a weaker claim
  than "processed in the EU". Already flagged in the roadmap.
  **Resolved 2026-08-14**, with one caveat that cannot be closed from the
  repository: `"regions": ["fra1"]` is set, but whether it takes effect must be
  confirmed on the next deploy, since the dashboard's own region setting can
  override the file. See `docs/roadmap-and-deployment.md`.

## 3. The plan

Ordered so that each stage leaves the app in a defensible state.

### Stage 1 — Make it giveable (half a day)

Nothing here is hard; all of it is blocking.

1. **F1** Fill `publisher` and `contactEmail` in `lib/legal-config.ts`. One
   file, one commit, unblocks the legal pages entirely.
2. **F2** Write real welcome copy in `messages/{en,fr}.json` and drop the
   scaffolding comment in `app/[locale]/(public)/page.tsx`. One or two sentences
   saying what Stap is — the README's own opening line is already better than
   what ships today.
3. **F3** Delete the "Change password" row and its `Profile.account.password`
   key. In a passwordless app the correct number of password settings is zero.

**Exit criterion:** a stranger can land on the app, read who publishes it, and
find no placeholder text on any public surface.

### Stage 2 — Fix what users will actually hit (one day)

4. **F5** `rhythm.tsx:78` → `const border = onHero ? ink : "var(--color-foreground)"`.
   One line; restores the confirmation screen in light mode.
5. **F4** Give the selected state a token that survives both themes. The
   cleanest fix is a dedicated `--color-selected-bg` (rather than reusing the
   hero), applied in all three call sites. Keep the amber-is-a-shape rule; an
   amber *border* or a check affordance would also satisfy 1.4.11 without
   touching the frozen palette.
6. **F6** Either restore the marker (`display: list-item` on the summary with
   flex on an inner `<span>`) or add an explicit chevron that rotates on
   `[open]`. Consider defaulting the tips open — they are good content.
7. **F8** Change the French `doneBanner` to "Un pas franchi aujourd'hui".
8. **F9** Drop the "New recap" badge until the seasonal review exists.
9. **F7** Owner decision — see the three options recorded under the finding.
   Note that the tempting one-line version (retime the crons) silently sends to
   nobody unless the stored slots are remapped with it, so this is not a patch
   that can be applied without choosing a direction first.

**Exit criterion:** every interactive state is visible in both themes; no UI
string promises something the system does not do.

### Stage 3 — Make it credible to a reviewer (two to three days)

10. **F15** Add Vitest plus a small, *pointed* suite. Do not chase coverage —
    target the logic that already has documented invariants, where tests read as
    design intent rather than as ceremony:
    - `lib/challenge.ts` / `challenge-config.ts` — the sliding level band and
      each fallback in the narrowing chain (ADR 0002).
    - `lib/game-content.ts` — deterministic seeding, and the F11 multi-word
      guard once added.
    - `lib/localize.ts` — the ADR 0001 accessor.
    - `lib/date.ts` — the UTC week/day boundaries.
    Then one Playwright smoke test that walks onboarding → challenge →
    validation, which is exactly the path where F4–F6 were hiding.
11. **F16** Add a GitHub Actions workflow running `tsc`, `eslint`,
    `content:check --strict` and the new tests on push and PR. A green badge in
    the README is worth more to a reviewer than another feature.
12. **F14, F13** Refresh the README status paragraph and delete the two stale
    comments. Cheap, and stale docs undercut the credibility the rest of the
    documentation earns.
13. **F12** Decide on `/design-system`: link it from the README as a live
    showcase (recommended — it is a genuine differentiator), or exclude it from
    the production build.

**Exit criterion:** a reviewer cloning the repo sees green CI, a focused test
suite, and documentation that matches the code.

### Stage 4 — Operational polish (deferred, non-blocking)

14. **F17** Set `"regions": ["fra1"]` in `vercel.json` after checking the plan's
    allowance.
15. **F10** Derive the onboarding teaser from the real first challenge, or
    soften it to a category rather than a specific promise.
16. **F11** Filter the fill game to multi-word phrases, falling back gracefully
    when a level cannot supply three.
17. Remaining v2 stubs (journal detail, seasonal review, weekly vocabulary) stay
    deliberately deferred — they are honestly labelled and do not block anything
    in Stages 1–3.

## 4. Assessment

The parts of this project that are usually weak in a portfolio app are strong
here: RLS on every table, authorisation enforced at every server action, an
open-redirect guard, a cron that fails closed, real GDPR export and hard
deletion, zero axe violations across both themes, complete i18n parity, and
architecture decisions recorded as ADRs. The production build is clean and the
core loop works.

The gap is not depth, it is finish. Three of the most visible defects — an
invisible selected state, invisible rhythm cells, and hidden tips — share one
cause: **there is no test or check that asserts a state is visible**, and axe
does not cover any of them. That is the same root cause as the missing test
suite, which is why Stage 3 matters beyond appearances.

Stages 1 and 2 are roughly a day and a half of work, and they move the app from
"impressive but visibly unfinished" to "genuinely shippable to other people".
